# `runregistrykit` 0.2.0

*Written by `interrupted-runs` prompt 06 on 2026-10-18, as of the tag `v0.2.0`. Every field,
value and behaviour below was measured on the package at that commit and at `v0.1.0`, by scratch
scripts built on each tree's own test fixtures in a temporary directory, on macOS 27 (`arm64`) with
Python 3.12.15; the campaign's log of prompt 06 holds the outputs. A `path:line` below is the
package's at the tag.*

## 1. What it is

`v0.2.0` follows `v0.1.0`. It is the release of the `interrupted-runs` campaign
([plan](../../prompts/interrupted-runs/README.md),
[board](../../prompts/interrupted-runs/IMPLEMENTATION_STATE.md)), which made the registry record
and judge a long job that may be interrupted:
- a run records the machine and the boot it ran on, and a run on another machine, or from an
  earlier boot of this one, is no longer judged by this machine's process table;
- `status.json` is written so that a signal handler's write can neither tear it nor lose a
  terminal state;
- a run whose status cannot be read, or does not say, counts as in use;
- `python -m runregistrykit end` records, on a person's word and after checking the evidence, a
  run whose end the registry never saw;
- `begin` refuses a store that a run which has not finished names.

The supported versions are unchanged ([`README.md`](../../README.md#supported-versions)). A client
adopts `v0.2.0` by moving its pin, in a commit of its own, after reading the adoption notes,
[`docs/adoption/v0.2.0/`](../adoption/v0.2.0/README.md).

## 2. What the registry writes

What changes is two `host` records, a state and an `ended` record that `end` writes, and the name
`status.json` is written through. Everything else is written exactly as `v0.1.0` wrote it (§2.5).

### 2.2 `status.json` written by `end`

`end` writes through the same writer as every other status write, so every field the status held
(`pid`, `host`, `units_done`, `units_total`, `stage`, a `fingerprint`, …) is kept, and `state`,
`exit_code`, `ended` and `heartbeat` are written. Measured:
- **a run here whose pid does not answer**: every key the running status had, `state` `"lost"`,
  `exit_code` `null`, and `ended` with `verified` `true`, `not_verified_because` `null`, and
  evidence `{"host": "this", "boot": "this", "pid_answers": false, "state": "running",
  "status_readable": true, …}`;
- **a run on another host, with `--unverified`**: `verified` `false`, `not_verified_because`
  `"another host"`, evidence `host` `"another"`, `boot` `null`, `pid_answers` `null`;
- **a status that could not be read** (torn), with `--unverified`: the status is composed from an
  empty one, so it holds **only** `state` `"lost"`, `exit_code` `null`, `ended` and `heartbeat`, and
  no `host`, `pid` or progress; `ended` has `verified` `false`, `not_verified_because` `"status does
  not say"`, and evidence `status_readable` `false`, `host` `"not recorded"`, and `state`, `pid`,
  `boot`, `heartbeat`, `heartbeat_age` and `pid_answers` all `null`.

A status that `end` refuses is not written. The manifest, `checkpoint.jsonl` and every sidecar are
not touched, and nothing is deleted.

### 2.3 `status.json`'s temporary names

`status.json` is written through a temporary name of each write's own, beside it,
`status.json.<pid>-<n>-<hex>.tmp` (the writing process's pid, a per-process counter, and eight
random hex characters; `_status_temporary_name`, `runregistrykit/__init__.py:292`), and then
replaced. It is created with the mode `open(path, "w")` gives, `0666` less the umask, as before
(measured `0644` under the umask `022`, at both tags). A process killed in the middle of a write
can leave one such file in the run directory. Nothing reads it, and a reader of `status.json` sees
the previous status or the new one.

**`status.json.tmp` is not one of them**: `v0.2.0` never writes `status.json` through it, where
`v0.1.0` did. `write_json_atomic` (`runregistrykit/__init__.py:260`) is **unchanged**: it still
writes through `<path>.tmp`, which the manifest and every sidecar write use (measured:
`manifest.json.tmp` and `<stem>.manifest.json.tmp`, at both tags).

### 2.4 Two forms of the status `host`

`begin` writes both `host` records **even when every value is `null`**, which means that the
platform offered none. A record with **no `host` at all** was written by `v0.1.0` (or by a writer
that is not the registry), and is read as §3 says.

### 2.5 What is unchanged

Measured by shape (every key, nested key and type) at both tags:
- **`checkpoint.jsonl`**: a ledger line is `unit`, `recorded`, `script_sha256`, `git_head`,
  `git_dirty` and `data`, as before;
- **the sidecar**: every field, before and after a fingerprint is recorded, as before; the store
  layer's format (`SIDECAR_FORMAT` 1) does not change;
- **the run directory's file set**: `manifest.json`, `status.json` and, with a ledger,
  `checkpoint.jsonl`, as before (`end` adds no file);
- **every key `v0.1.0` wrote** in the manifest and `status.json`, with its meaning: the manifest's
  `run_id`, `created`, `purpose`, `campaign`, `prompt`, `argv`, `cwd`, `script`, `script_sha256`,
  `unit`, `expected_units`, `checkpoint`, `results`, `results_store_id`, `scope`,
  `heartbeat_means`, `git_head`, `git_dirty` and `packages`; the status's `state`, `units_done`,
  `units_total`, `pid`, `exit_code`, `heartbeat`, `stage`, and `finish`'s `fingerprint`,
  `fingerprint_sidecar` and `fingerprint_error`.

`packages.runregistrykit.version` records the installed distribution's version, so a run begun
under `v0.2.0` records `0.2.0`.

### 2.6 What `id` and `boot` are, and what a `null` means

From `this_host()`'s docstring (`runregistrykit/__init__.py:578`) and
[`prompts/interrupted-runs/01-the-host.md`](../../prompts/interrupted-runs/01-the-host.md):
- **`id`** is the first 16 hex characters of the SHA-256 of a fixed prefix and the machine's own
  identity: on macOS `gethostuuid(3)`, on Linux the first non-empty of `/etc/machine-id` and
  `/var/lib/dbus/machine-id`. **The identity itself, a hardware identifier, is never written**;
  only the digest is. It survives renaming the machine and changing its network.
- **`boot`** is the identity of the current boot, as the system gives it: on macOS the sysctl
  `kern.bootsessionuuid`, on Linux `/proc/sys/kernel/random/boot_id`. It changes at every boot.
- **`name`** is `RUNREGISTRYKIT_HOST_NAME` if it is set and not empty, else `platform.node()`. It
  is for a person to read; the registry never judges by it.
- **A `null`** in `id`, `boot` or `name` means that the platform offered none when the record was
  written: on macOS, a failing `gethostuuid` or an all-zero answer for `id`, or a failing sysctl
  for `boot`; on Linux, no machine-id file of 32 hex characters, or no `boot_id`; on any other
  platform, always, for `id` and `boot`. On macOS (measured here) and on Linux (CI's
  `ubuntu-24.04` runners, where the suite's identity tests ran) both were given. `machine`,
  `system`, `release` and `python` come from the `platform` module and are strings, possibly
  empty.

A container whose `/etc/machine-id` came with its image has the same `id` as every container made
from that image; the package does not tell them apart (not measured).

## 3. A record written by `v0.1.0`, read by `v0.2.0`

Every existing run directory reads as it did. Measured, with records written by `v0.1.0`'s code in
the runs root `v0.2.0` reads:
- **A status with no `host`**, or a `host` whose `id` is `null` or that is not an object, is judged
  by its pid and its heartbeat, as `v0.1.0` judged it: a live run is `alive`, a dead one `stale`,
  a finished one `finished`, each with the marker `v0.1.0` gave it. `list` counts it in its new
  summary clause, "*N* with no host recorded", and `list_runs` gives it `host_recorded` false.
- **`checkpoint.jsonl` and the sidecar** are read as before.
- **What changes in judgement**, on old records as on new ones:
  - a run whose status cannot be read (missing, torn, not JSON, not an object), or says no state
    the registry writes, now **counts as in use** by `copy`, `move`, `fingerprint`, `retire`,
    `amend` and `begin`, and `list` marks it `!!` when it has a manifest. `v0.1.0` counted only a
    `running` one. The registry cannot tell whether such a run is running, and errs towards in use;
  - a `status.json` or `manifest.json` that is JSON but not an object (`[1]`) is **read as
    unreadable**. `v0.1.0`'s `list_runs` and `liveness` raised `AttributeError` on it, so `list`
    and every store operation under that runs root raised; `v0.2.0`'s read it, the status as
    `unknown` and the manifest as none (`has_manifest` false);
  - a `running` run is now in use for `begin` as for the store operations (§5).

## 4. A record written by `v0.2.0`, read by `v0.1.0`

A client pinned at `v0.1.0` in one checkout may read a runs root that `v0.2.0` writes in another.
Measured in one runs root, each run on a store of its own, read by both tags' code. An "alive" pid
is a child process alive while both tags read (both read `pid_alive` true for it); a "dead" one is
a child started and reaped before. "Begun" means a second `begin` with `results` on the run's
store returned a run.

| Written by `v0.2.0` | `v0.1.0`: `liveness`, `list` | `v0.1.0`: `fingerprint_store` | `v0.1.0`: second `begin` | `v0.2.0`: `liveness`, `list` | `v0.2.0`: `fingerprint_store` | `v0.2.0`: second `begin` |
|---|---|---|---|---|---|---|
| alive | `alive`, no marker | refused, alive | **begun** | `alive`, no marker | refused, alive | refused |
| stale (dead pid) | `stale`, `!!` | refused, stale | **begun** | `stale`, `!!` | refused, stale | refused |
| `done` | `finished` | proceeds | begun | `finished` | proceeds | begun |
| `lost` (by `end`) | **`unknown`**, no marker | proceeds | begun | `finished` | proceeds | begun |
| `foreign`, alive pid | **`alive`**, no marker | refused, as alive | **begun** | `foreign`, `??` | refused, on another host | refused |
| `foreign`, dead pid | **`stale`**, `!!` | refused, as stale | **begun** | `foreign`, `??` | refused, on another host | refused |
| earlier boot, alive pid | **`alive`**, no marker | refused, as alive | **begun** | `stale`, `!!` | refused, stale | refused |
| earlier boot, dead pid | `stale`, `!!` | refused, stale | **begun** | `stale`, `!!` | refused, stale | refused |
| status torn | `unknown`, **no marker** | **proceeds** | **begun** | `unknown`, `!!` | refused, cannot be read | refused |
| status `[1]` (JSON, not an object) | **`list_runs` raises** `AttributeError`; `list` exits 1 with a traceback | **raises** `AttributeError` | begun | `unknown`, `!!` | refused, cannot be read | refused |

`list` exits 0 at both tags in every row but the last. `v0.1.0` counts a `lost` run and a torn one
as `unknown` in its summary, with no line on stderr for them, and has no `foreign` count and no
host count. The last row was measured in a runs root of its own, beside an alive run of each tag:
under `v0.1.0`, a status that is JSON but not an object makes `list_runs` raise for the whole runs
root, so `list` raises, and `fingerprint_store` raised for every store there, the alive runs' too;
`copy_store`, `move_store`, `retire_store` and `amend_sidecar` read the runs root through the same
`list_runs` at `v0.1.0`.
`v0.1.0`'s `begin` makes no check, so it begins in every row. A run with no host, written by
`v0.1.0`, is read alike by both tags (§3).

**What a `v0.1.0` reader loses:**
- it **tests a `foreign` run's pid here**: a pid that names a process on another machine is judged
  by this machine's process table, alive or stale by chance;
- it judges a run from an **earlier boot** of this host by its pid, which may now name another
  process;
- it calls a **`lost`** run `unknown`, a state it does not know, though it does not count it as in
  use;
- it does not count a run whose status cannot be read as in use, and raises on one that is not an
  object;
- **its `begin` does not refuse a second writer**: a `v0.1.0` checkout begins a run on a store that
  a `v0.2.0` run is writing.

**Advice:** every checkout that shares a runs root moves to `v0.2.0` together.

## 5. The public interface

By `__all__` and `inspect.signature` of every public name of `runregistrykit`,
`runregistrykit.stores`, `runregistrykit.client`, `runregistrykit.fingerprint` and
`runregistrykit.__main__`, at both tags. Every public name not listed here is unchanged in name
and signature.

- **`this_host() -> dict`** is new (`runregistrykit/__init__.py:578`): `{"id", "boot", "name",
  "machine", "system", "release", "python"}` for this machine now, read afresh on each call (§2.6).
- **`TERMINAL_STATES`** is `("done", "failed", "killed", "lost")`, where it was `("done",
  "failed", "killed")`. `lost` is the state `end` records; `Run.finish` accepts it, as it accepts
  any terminal state, but a caller reporting how its own run ended uses one of the other three. A
  comparison of a state with the three, or a test that the set is exactly three, sees a fourth.
- **`liveness(status, stale_after, now=None, *, here=None) -> str`** gains the keyword `here`, a
  `this_host()` dict (read afresh when it is not given and a record needs it), and the value
  **`foreign`**, for a `running` record on another host. Its values are `alive`, `stale`,
  `foreign`, `finished` and `unknown`. A `running` record from an earlier boot of this host is
  `stale` whatever its pid; `lost` is `finished`; a status that is not an object is `unknown`,
  where it raised.
- **`pid_alive(pid)`** returns `False` for a pid outside the platform's range (`2**31` here), where
  it raised `OverflowError`. Its signature is unchanged. A caller that relied on the raise sees
  `False`.
- **`list_runs`**' entries gain four keys: `host` (the manifest's `host.name`, or `None`),
  `host_id` (the status's `host.id`, or `None`), `host_recorded` (whether the status has a `host`
  object) and `status_readable` (whether `status.json` parsed as a JSON object). It no longer
  raises on a manifest or status that is not an object (§3).
- **`begin`** raises `RuntimeError` when its `results` store is named by a run that has not
  finished, under the runs root it creates the run in, by path or `results_store_id`: `running`
  (alive, stale or on another host) or a status that does not say. The message begins `Cannot
  begin run <id> with results "<store>":`, describes each such run, names `python -m
  runregistrykit end RUN_ID --reason TEXT` for a stale one, and ends `No run directory was
  created`. There is no override, and it is a check and not a lock. Its signature is unchanged.
- **The store operations** (`copy_store`, `move_store`, `fingerprint_store`, `retire_store`,
  `amend_sidecar`) **count every run whose status does not say it has finished**, where they
  counted only a `running` one, and their refusals' remedy names `python -m runregistrykit end
  RUN_ID --reason TEXT` in place of `Run.finish`. A run on another host is described as "running
  on another host, <name> (pid <pid>, not tested here)", with a sentence on ending it there or
  with `--unverified`; a status that cannot be read, or says neither running nor finished, is
  described as such, with a sentence naming `--unverified`. **A caller that compared a refusal's
  text must re-read it**: the remedy sentence changed (04), and what is counted and described
  changed (03). The fragments `run <id> is running` and `names this store` are kept for a
  `running` run on this host.
- **`list`**: the marker `??` for a `foreign` run, whose row names its host; `!!` also for a run
  with a manifest whose status does not say; the summary line gains "; *N* with no host
  recorded."; on stderr, the stale line adds "or this machine has rebooted since" and "Once you
  know one is over, end it with `python -m runregistrykit end RUN_ID --reason TEXT`.", and two
  lines are new, one for runs whose status does not say (naming `end … --unverified`) and one for
  runs on another host.
- **`python -m runregistrykit end RUN_ID --reason TEXT [--unverified] [--root DIR]`** is new (§2.2;
  [`README.md`](../../README.md#ending-a-run-whose-end-was-never-recorded)). The top-level
  `--help` lists it and says what `copy`, `move`, `fingerprint`, `retire` and `amend` now refuse.
  Its function is private; `__all__` of `runregistrykit.__main__` is still `main`.

## 6. Known issues

The open entries of the campaign's board, §3, as they stand at the tag:
- [`[02b-a-raising-handler-can-leave-the-status-lock-held]`](../../prompts/interrupted-runs/IMPLEMENTATION_STATE.md#02b-a-raising-handler-can-leave-the-status-lock-held):
  at Python 3.14 only, a signal handler that raises just after `with _STATUS_LOCK:` has taken the
  lock leaves it held by the thread that was writing, as a bare `with` over an `RLock` does at
  3.14.8; fixed at 3.12 and 3.13, and no client or CI runs 3.14.
- [`[03-a-run-whose-manifest-cannot-be-read-names-no-store]`](../../prompts/interrupted-runs/IMPLEMENTATION_STATE.md#03-a-run-whose-manifest-cannot-be-read-names-no-store):
  a `running` run whose `manifest.json` is missing, torn or not JSON names no store, so copy, move,
  fingerprint, retire, amend and `begin` do not count it on the store it is writing; no known cause
  tears a manifest in a run's life.
- [`[03-a-run-on-a-manifest-that-is-not-an-object-raises-where-it-is-used]`](../../prompts/interrupted-runs/IMPLEMENTATION_STATE.md#03-a-run-on-a-manifest-that-is-not-an-object-raises-where-it-is-used):
  `Run(path)` on a manifest that parses but is not an object constructs, then `checkpoint_path`
  and `results_path` raise `AttributeError`; low impact, since the manifest is written once and
  never rewritten.
- [`[03-store-show-raises-on-a-state-that-is-a-list-or-an-object]`](../../prompts/interrupted-runs/IMPLEMENTATION_STATE.md#03-store-show-raises-on-a-state-that-is-a-list-or-an-object):
  `store show` ends in a `TypeError` traceback when a run naming the store has a `state` that is a
  JSON list or object; no writer of the registry records one.
- [`[04-a-killed-process-not-yet-reaped-answers-kill-0]`](../../prompts/interrupted-runs/IMPLEMENTATION_STATE.md#04-a-killed-process-not-yet-reaped-answers-kill-0):
  a killed process that its parent has not reaped answers `kill -0`, so `liveness` calls its run
  `alive`, `end` refuses it as a live pid, and `begin` refuses its store, until the parent waits
  for it or exits; the registry errs towards in use, which loses nothing.
